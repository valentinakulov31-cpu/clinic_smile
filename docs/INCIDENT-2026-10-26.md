# Public Lead Submission: 2026-10-26

## Cause

The public create views inherited Django REST Framework's session authentication.
When a browser had a valid Django admin session, a request without an X-CSRFToken
header failed with HTTP 403 before validation or database insertion. The same
request from an anonymous visitor did not require CSRF. The frontend sends
same-origin session cookies even when its optional cross-origin credentials flag
is false.

The issue predates the email-recipient change. Enabling notifications on October
18 did not change authentication or the deployed backend source. A direct SMTP
test and anonymous API tests did not cover the logged-in browser case.

The fix disables authentication only on the public create-only lead endpoints
and explicitly declares AllowAny. No session privileges are used by these views.
Admin CSRF, permissions, input validation, honeypot and rate limiting remain in
place. Regression tests cover all four endpoints with and without an admin
session, email generation, validation, rate limiting and admin CSRF enforcement.

## Observed Impact

Snapshot collected at 2026-10-26 04:22 Asia/Krasnoyarsk, before diagnostic
submissions. Nginx access logs cover 2026-10-11 07:53 through 2026-10-26 04:20.
Rotated and compressed access logs were included.

- October 19 through the snapshot: three lead POST requests, all HTTP 403,
  at 03:59:33, 03:59:38 and 03:59:40 on October 26.
- Those three attempts share one IP/user-agent pair. The same browser accessed
  authenticated admin pages immediately before submitting the form.
- October 12 through the snapshot: eleven lead POST requests: seven HTTP 201,
  one HTTP 429 and the three HTTP 403 responses above. No HTTP 5xx lead responses.
- The HTTP 429 was a repeated attempt on October 18 between two successful
  submissions from the same IP/user-agent pair.
- Seven corresponding database rows exist for the seven successful requests.
  No new database rows were recorded on October 19-25.

Three rejected HTTP attempts are confirmed; three lost customers are not.
The grouped failures look like retries by one admin browser, so the evidence
supports approximately zero to one potential lead, depending on whether those
attempts were testing or a real enquiry. IP/user-agent grouping is only a proxy
for a person. Server logs cannot quantify browser-side failures that never
reached the server, or people who abandoned the form. Rejected request bodies
are not logged, so their names and phone numbers cannot be recovered from access
logs. Existing saved leads are unaffected.

## Production Verification

Revision abfb14a893f18a002331ae42bb3b6697a0a94472 was deployed to
/opt/clinic_smile/releases/20261026-lead-session. The database and previous source
were backed up under /opt/clinic_smile/backups/20261026-lead-session. No database
migration or frontend change was needed. The local regression suite passed all
48 tests.

Real HTTPS requests with a temporary authenticated admin session confirmed that
all four public endpoints return validation errors rather than CSRF failures.
Admin writes without a CSRF token still return 403. A synthetic appointment
returned 201 and was saved as lead 16 at 04:34 Asia/Krasnoyarsk. Only that
explicitly labelled test was marked canceled; the temporary session was deleted.
All 15 rows present immediately before the live verification were preserved,
including lead 15 submitted separately at 04:29 after deployment.

## Separate Email Delivery Problem

Postfix logs show Mail.ru accepted the direct SMTP test on October 18 but rejected
notification messages for saved leads 13 and 14 on October 18, lead 15 on October
26, and synthetic lead 16 with `550 spam message rejected`. These are delivery
failures, not lost database records. Mail.ru acceptance cannot be claimed for the
live verification. The mail queue was empty after the bounces.

This fix does not resolve the receiving provider's spam rejection. PTR still
returned provider hostnames instead of mail.ulybnis24.ru during the audit;
SPF included the server IP and DMARC was present. These observations alone do
not establish the exact reason for Mail.ru's filtering decision. Rejected email
notifications require separate mail-deliverability remediation or an authenticated
SMTP relay. No existing lead data or recipient configuration was changed.
